---
name: contract-timeline
description: Reads an executed real estate purchase contract (with riders, addenda and counteroffers) and lays out every deadline, from the Effective Date and deposits through inspection, appraisal, loan approval, title, walk-through and closing, from the buyer's or the seller's side, with who owes each one, the action and what happens if it's missed. Florida FAR/BAR contracts (AS IS and Standard, every rider and addendum) are fully supported; any other contract is read on a best-effort basis from its own dates and time rules. Use it whenever an agent has an accepted or executed contract and asks for key dates, deadlines, a contract timeline or closing calendar, "when does the inspection period end", "what's due next", a deadline summary for a client, or when an amendment or extension is signed and the dates need to be re-run. Not for writing or analyzing offers before acceptance.
---

# Contract Timeline

Turns an executed contract into a timeline of every deadline. The dates come from a script, never mental math, because one wrong day can cost a client their deposit.

Two views of the same dates: the **buyer view** highlights the buyer's actions and when their protections end; the **seller view** highlights the seller's obligations and until when the buyer can still cancel. Use the side the agent represents, and ask if it's unclear.

## Guardrails

These apply to everything this skill writes: files, chat replies, and text the agent may forward to a client.

- **Fair housing.** Flags and notes are about dates, terms and documents, never about the buyer, the seller or the neighborhood. Describe the property, the numbers and the terms, never people: not who the home suits, who should buy, or who lives nearby. No claims about safety, crime, school quality or who makes up an area. If the agent asks for wording that breaks this, write the compliant version and say why in one sentence; don't lecture or flag innocent wording like "family room".
- **No em dashes in prose,** chat included: use a comma, colon, parentheses or a new sentence. A lone em dash for an empty value (a table cell with nothing in it) is fine.
- **Labels in Title Case:** headings, column headers, row names, tiles, legend entries, card and slide titles. Sentences, notes and table values stay sentence case.
- **Names, not pronouns.** In chat and in notes, call a client by name or "the buyer" / "the seller"; never infer a pronoun from a name.
- **Contract support.** Only Florida FAR/BAR contracts (AS IS and Standard, with their CR-7 riders and addenda) are fully supported. For any other contract the script output has `support: "best_effort"` and the line to use in `chat_notes`: say it once in chat, in your own short words. The same goes for a note that a FAR/BAR contract isn't the revision the rules were checked against. Never put either in a PDF, calendar file, worksheet or markdown report.
- **`render.py` checks the data file first** (and any deck, CMA or profile file it reads) and stops on an em dash in a sentence, a clear fair-housing red flag, or tool words, data keys, ISO dates or jargon in client text (`references/client-wording.md`), listing every field at once. Rewrite each field; don't work around the check. Labels are put in Title Case for you. It can't see chat replies, so the rules above still apply there.

## 1. Read the Executed Documents

Read the whole package: contract, every rider and addendum, and every counteroffer (`pdftotext -layout`). Record the terms in a deal file: read `references/deal-file.md` for the format.

- **Scanned or image-only pages** (`pdftotext` returns nothing), and checkboxes or X marks whose column the text can't place: render the pages with `pdftoppm -r 110 -png` and read them as images; crop and render at 300 dpi (`-r 300 -x -y -W -H`) to read Dotloop time stamps, initials and checkbox states. Never guess a value you can't read: say which page and ask for a clearer copy. On a scan, read these pages and skip the rest unless one points elsewhere (the Standards pages and most disclosure pages set no date): the contract's Paras. 1 to 3 and the pages holding Paras. 4, 8, 9 and 12 (price, deposits, dates, periods), the rider checklist (Para. 19) and Para. 20, the signature page with its initials and time stamps, every attached rider that has a blank or a date, every counteroffer or amendment page, and the escrow receipt.
- **The agent uploads a deal file (JSON) and no package:** accept it as the working file. Copy it to the temporary folder, read the facts from it, add what the agent's message changes (an amendment, a receipt date) and run the scripts on it. Say in one line that the dates come from their file, not the signed documents. If it has `"sample": true`, still render the report (it prints SAMPLE DATA) and, in the same reply, ask whether this is a real deal; for a real one, remove the flag and re-render. Never hold the files back for the answer.
- **Terms typed in chat, no package or deal file:** build the deal file from the agent's message (cite it in `effective_date_source`) and ask only for what would change a date; don't ask for the package first.
- **The script finds a problem in the agent's own file** (a `problems` error, a `warnings` item, or an agent note such as a field that doesn't fit the riders or the financing): fix what is plainly a typo (a misspelled field name, a date with the month and day swapped when only one reading is a real date) and say what you changed in one line. Anything that could be a real term (a period that doesn't match the form default, a rider field without the rider) stays as the agent gave it: deliver the timeline from it and ask the question in the same reply, with the date that would change if the answer is no. That date is in the note and in the output's `if_changed`: never build a second deal file to find it.

- **Not executed yet** (only one party signed or initialed): stop before the scripts. Say what's missing and list the terms that set a date: price, deposit amounts, and the dated periods, each with its days or its form default for a blank (initial and additional deposit, inspection, loan application and approval, title evidence, closing date, and each attached rider's periods, such as AGA-1's 30-day valuation period or Rider GG's 3 days), labeled "form default". Leave out defaults that set no date (repair limits, walk-through, a flood window the disclosures rule out). Offer to build the timeline once it's signed; run a what-if only when the agent gives the expected Effective Date. If the acceptance time in Para. 3 (or the contract's own) has passed, say so and suggest confirming with the other agent; never say the offer lapsed or is void.
- **Effective Date** is when the last party signed or initialed **and delivered** the final counteroffer or acceptance, not the offer date. Write down the evidence: `effective_date_source` says whose signature or initials on which document, with no date or time in it (the script refuses one), and `effective_date_signed` holds the stamp (`YYYY-MM-DD HH:MM`); the report prints both. Ask for the delivery date when it differs from the signature date. When the package shows signing times but no delivery (an e-signature log), use the last signature or initial, set `effective_date_delivered: false` (the script's note asks for the delivery date; don't write your own) and go on. Never name the e-signature platform in `effective_date_source`: it prints on the client's report. A contract that defines the Effective Date by the last signature alone (not delivery) follows its own definition (`references/other-contracts.md`). With two or more buyers or sellers, it's the last of all their signatures or initials plus delivery, never the first signer's time. If it's ambiguous, or later than today for a contract the agent calls executed, stop and ask: every deadline depends on it (the script adds an agent note when it's after the report date). A future date is fine for a what-if ("if we go under contract on the 20th"): set `what_if: true` so the PDF and calendar say What-If and the script skips its confirm-the-date note. A future date the agent neither calls executed nor hypothetical ("effective 11/20/2026") is a what-if too: answer it and ask once whether the contract is signed.
- **A counter made on the contract itself** (the seller checks "Seller counters Buyer's offer", strikes terms and initials the changes): the Effective Date is the last party's last initial or signature on the changed terms, once delivered. Cite Para. 3(b) in `effective_date_source` ("Buyer's last initial on the seller's changes to the contract (Para. 3(b))", with the stamp in `effective_date_signed`), never the paragraph whose value changed. The time to accept that counter is Para. 3(a)'s (2 days after delivery unless another time is written), not the buyer's original offer deadline. To find the changes, look for the countering party's initials or time stamps next to a line (in `pdftotext`, search for their initials), then render that page and read which value is struck and which is written in. Rules: `references/farbar-addenda.md`, CO-3, Counter on the Contract.
- **Later documents win:** counteroffers override the offer; initialed handwritten changes override typed text. With more than one counter, record which counter set each term in `counter_chain` (`references/deal-file.md`) so a re-run in this conversation doesn't have to reread them. When two documents disagree on a fact (a condo document receipt date), use the later signed one and say the difference in an agent note keyed to that row. If something is illegible, flag it instead of guessing.
- **Already done:** an escrow receipt in the package means the deposit is in: record it in `completed` with the receipt date (`references/deal-file.md`), and the same for anything else performed that the package or the agent shows (a document signed and delivered, such as Rider GG's compensation agreement). The end of a contingency or cancel window is never done before its date (the script refuses it), unless the buyer ended it early in writing (a signed waiver, written loan approval delivered): then list its key in `ended_in_writing` too. The one the script closes itself: once Rider GG's agreement is done, Compensation Contingency Ends can't arise, so it shows done, off page 1 and the calendar. Done rows show as done and drop out of the calendar reminders.
- **Short sale (Rider G):** only the deposit, the short sale rows and Rider GG count from the Effective Date; every other period and the closing count from the buyer's receipt of the approval (`references/farbar.md`). Until `short_sale_approval_received` is recorded they stay pending, and the report and calendar still work. Record Para. 7's back-up offer box (`short_sale_backup`) so the agent note says whether the seller may take back-up offers.
- **FAR/BAR contracts (Florida):** read `references/farbar.md` for where each date goes in the deal file and the defaults for blanks, `references/farbar-riders.md` for every rider attached (deadlines, defaults, what changes; it is long, so read only those riders' sections from its Contents), and `references/farbar-addenda.md` for any addendum (counteroffer, extension, escalation, appraisal gap, co-op). Check the package with `references/farbar-package-check.md` (riders checked vs. attached, RESERVED riders on AS IS). `references/farbar-contract.md` has every paragraph of both forms when you need one. **Dated defaults:** leave a blank period out of the deal file (never write the default in); the script adds an agent note for each one it fills (every period and rider date in `references/farbar.md`, and the closing time). A period the form prints as a fixed term (the survey's 5 days, the walk-through, Rider P's 10 days) isn't a blank: no note, and never in `blanks`. List each blank you saw in `blanks`, by the field names in `references/deal-file.md`. A term your copy doesn't show (a partial copy or text extract) takes the default the same way: leave it out, and the note reads "not given"; the reply asks in one line, with the defaults, to confirm those terms on the signed contract. Terms that set no date follow the rule below.
- **Notes.** The report's "Check:" lines (`flags`) come only from the script, in its words; the deal file has no `flags` (an old one's become agent notes). Your notes go in `agent_notes` and stay in chat: defaults used for blanks, readings to confirm, a difference between documents, anything that would confuse a client. These are agent notes, each with the question to ask: a blank with no default (Rider H's premium caps) and a document the timeline depends on that wasn't uploaded (Rider GG's compensation agreement). Record the Para. 2 amounts, the pre-approval, the Rider H boxes, the flood zone, who occupies the home (`occupancy`), whether it was built before 1978 and the Standard form's repair limits (`references/deal-file.md`, `references/farbar.md`): the script checks the money and writes those notes itself.
- **Terms that set no date** (Rider H's premium cap, Rider F's minimum value, Rider E's repair cap, Rider U's rent, Rider A's Para. 9 boxes, the date the SIRS arrived when it came with the condo documents): the deal file has no field for them. Read them from the contract text and mention them in an agent note only when there's a question to ask (a blank, a figure that looks wrong); otherwise leave them out. A blank one that takes a form default is asked, not listed as a default. The Standard form's blank repair limits are the script's note (`repair_limits`, in dollars), never your arithmetic.
- **Revision:** record `form_revision` and, when you read it from the form's footer, `"form_revision_source": "footer"`. A revision from anywhere else (a header, a summary, the agent) is recorded as given, never made into a footer string.
- **Amendments dated after today:** ask the agent to confirm the signing date before using them.
- **Any other contract** (another state's form, a builder contract, the Florida Realtors CRSP): read `references/other-contracts.md`. You list the deadlines yourself, and the time rules come from the contract's definitions (only `day_count` is required; ask about the rest rather than fill them in); nothing about another state's forms is built in.

## 2. Compute

Write deal.json in a temporary folder, never the outputs folder (`references/saved-files.md`, Working Files).

Florida rules are built in; for any other contract the time rules come from the contract (never estimated).

```
python3 scripts/timeline.py deal.json [--side buyer|seller]   # --side overrides the deal file's side
```

It prints every date already formatted, or `ok: false` with `problems` to fix. `warnings` are for you (`render.py` prints them too): a contract field or `blanks` name the script doesn't read (most often a misspelled name that would drop a deadline). Fix each and re-run; never pass one on. Spot-check before going further: the deposit and loan application dates, anything extended to the next business day, and a closing date that extended past a weekend or holiday.

The script adds its own `flags` and `agent_notes` (listed in `references/deal-file.md`, Script Notes), each with a stable key in `flag_keys` and `note_keys`; don't add those yourself. Run the script before writing your own notes, and add one only when its subject isn't among the `note_keys`. Notes are matched by key, never by wording: when yours is about a script note, give it that key (`{"key": "money_mismatch", "text": "..."}`, `"default:title"`) and the script keeps its own; when it's about a deadline, give it the row's key and the script starts it with the row's label and date. Pass the `agent_notes` on in plain words, never restated as a second line in your own words, and the `chat_notes` once.

## 3. Deliver

**Quick question** ("when does the inspection end?", "what's due this week?"): answer from the output in a sentence or two, plus at most one line on the rule used or what to confirm. A deal file with just the Effective Date, the time rules and the one deadline is enough; leave the closing date out if you don't have it (dates counted back from closing then wait for it). Pass on only the notes that bear on that one date (an open time rule), not the rest. Two cases to answer rather than stop on:

- **The day count isn't known** (another state's contract, and the agent didn't say calendar or business days): run the script once with `"day_count": "calendar"` and once with `"business"`. Lead with the calendar-day date and give the business-day date second, in one line ("Fri Nov 27 at 5:00 PM counting calendar days; Wed Dec 2 if the contract counts business days, so check its definitions"). Never pick one silently.
- **A future Effective Date** the agent didn't call executed ("if we sign on the 20th", "effective 11/20"): answer it as a what-if, say so in the same line, and set `what_if: true` in the deal file; for a contract the agent calls executed, confirm the date first (Section 1). **Full timeline in chat:** fill in `assets/timeline-template.md` with the output's values. **A report to send or print:**

```
python3 scripts/render.py deal.json [--format pdf|ics|all] [--profile profile.md] [--date YYYY-MM-DD] [--lender-dates]
```

`all` (the default) saves the PDF and a closing calendar (`.ics`: one event per dated contract deadline not yet done, a reminder the day before each critical one) that the agent or client can import into any calendar app. The lender's targets (insurance bound, Closing Disclosure) are estimates, so they're in the PDF but not the calendar; `--lender-dates` adds them, titled "Lender Target", when the agent asks. It saves the PDF to the outputs folder; `--profile` puts the agent's name and brand colors on it (found as `references/saved-files.md` describes). The PDF's Prepared date is today: when the agent states today's date ("Today is September 26"), set `report_date` in the deal file to it (or pass `--date`), since Past, Confirm and the first deadline count from it, and never question it against the computer's clock; otherwise the system date is used. If it can't render, say so and give the markdown timeline instead.

With the PDF, the chat reply doesn't repeat the report. It must contain, in plain words:

1. A small table of the key dates only: the first deadline (`first_deadline`) and who owes it, when the contingencies end, and the closing. Who is the row's `party` as the report prints it (Buyer, Seller, Both), never another word for it. `first_deadline` is the earliest open dated row (not done or past) from the report date, whoever owes it (Rider GG rows only while open, lender targets never), the same row the PDF's Next deadline names.
2. Every deadline marked Past, Confirm (ask whether it was met, then record it in `completed`).
3. Every flag, and every agent note, each as one line with its question: check each `note_keys` entry is in the reply, merged or not, never dropped. Under a questions heading put only questions, grouped by who acts: the buyer's items, then the seller's, then both parties' or the agents' paperwork, numbered 1, 2, 3 straight through the groups (or bullets throughout, never both). Ask only what changes a date or a term; a reading that changes nothing in practice isn't a question. A fact with nothing to answer (a Para. 20 promise the seller made) goes with the key dates, not under the questions.
4. The chat notes once, `render.py`'s calendar line when it prints one (the lender's targets left out of the calendar), and the other format offered in one line.

Nothing else: no recap of checks that passed. Aim for 450 words outside the tables, 550 at most on a big deal (several counters, a short sale, many notes). When it doesn't fit, cut in this order and never drop a question or a flag: the form defaults used go on one line ("Form defaults for blanks: deposit 3 days, loan application 5 days, title 15 days before closing"); questions that share an answer merge into one; a note the PDF already shows (a Check line, a pending row's rule) becomes "see the report"; then shorten each remaining line. Keep the deal file in the temporary folder for re-runs in this conversation (`references/saved-files.md`, Working Files); never present or offer it.

## Amendments and Extensions

Add the amendment to `amendments` in signing order, with its form or title as `name` ("Extension Addendum (EA-4)", "Addendum No. 1") so the notes name it as the agent knows it (format in `references/deal-file.md`; an extension of N more days adds N to the period's day count, and the script's agent note gives the later reading when the original end had rolled), re-run, and answer with the output's `moved` list in its order (the closing first when it moved, then the rest by date): one line per moved deadline, "Closing: Fri Nov 6 · 10:00 AM (was Fri Oct 30)", then the `newly_dated` rows (dated for the first time, such as every period after a short sale approval), then anything the move made tight (flags). This replaces Deliver's reply list on a re-run: after what moved, repeat only the flags, notes and Past, Confirm rows the amendment changed or that are newly due. On the first run in a conversation, when the package already includes amendments, the agent hasn't seen any notes yet: give the full Deliver reply, with what the amendments moved after the key dates. The report compares the original contract with the current one and shows moved dates as "was".

In this conversation, add it to the deal file in the temporary folder. In a later conversation, or when no deal file exists yet, rebuild the deal file from the executed package (the contract as first signed) and add each amendment to `amendments` in signing order, so the report still shows the "was" dates. The deal file is a working file: never hand it to the agent (`references/saved-files.md`).

## Limits

Dates are computed from the documents as recorded; the documents control. Lender dates (insurance bound, Closing Disclosure) are estimates. Recommend the escrow or title agent confirm the timeline, and a real estate attorney for any dispute about deadlines. Not legal advice.
